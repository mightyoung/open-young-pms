# PMS 业务主线瘦身改造计划

更新时间：2026-06-22

## 1. 背景与目标

当前系统已经具备项目、任务、隐患、审批、合同、质量、风险、资源、报告、论坛、AI、组织、数据治理等能力，但产品定位仍应回到 `SPEC.md` 中定义的“面向单部门工程项目管理的全流程数字化平台”。本计划的目标不是一次性删除功能，而是先收敛信息架构和业务主线，把系统从“多模块堆叠”调整为“围绕项目交付闭环”的项目管理系统。

目标业务主线：

```text
项目立项/项目流程 -> WBS/任务/甘特 -> 现场隐患/问题上报 -> 整改/审批 -> 报告/看板 -> 归档
```

## 2. 设计原则

- 保留 React + Vite + Ant Design + FastAPI + SQLAlchemy 主栈，不做框架替换。
- 保留 `src/features/*` 与 `backend/api/routers/*` 作为新能力主路径，不新增 `src/pages/*.jsx` 和 `backend/routers/*` legacy 面。
- 先隐藏或合并入口，再决定是否删除后端能力，避免破坏已有数据结构和接口。
- 顶级菜单只服务高频主流程；低频、配置型、项目附属型能力进入项目详情、个人入口或系统管理。
- 优先把项目、任务、隐患、报告四条核心链路从 mock/静态数据收束到真实 API，再扩展非主线模块。

## 3. 当前问题摘要

### 3.1 顶级入口过多

`src/app/route-map.js` 已经把论坛、草稿箱、风险、质量、组织、AI、合同、审批中心、数据治理等都注册为业务入口。`src/app/menu.config.js` 也将多个模块提升到顶级菜单。这会削弱项目交付主线。

### 3.2 非主线模块独立成系统

合同、资源、风险、质量对工程项目有价值，但它们更适合作为项目详情中的附属对象，而不是与“项目管理”并列的独立业务系统。

### 3.3 核心链路尚未夯实

项目、任务、隐患、报告、风险、质量等前端 hook 中仍存在 mock 数据或空数据兜底。当前最需要补强的是主线真实数据闭环，而不是继续扩展横向模块。

### 3.4 部分契约尚未对齐

审批中心前端使用 `/approval/tasks`，后端实际实现了 `/approval/my-tasks` 和 `/approval/tasks/{id}/approve` 等接口。瘦身阶段需要同步修正这些主链路契约问题。

## 4. 目标信息架构

### 4.1 顶级菜单

第一版建议顶级菜单收敛为 7 项：

1. 仪表盘
2. 项目管理
3. 任务管理
4. 随手拍/隐患
5. 报告中心
6. 审批中心
7. 系统管理

### 4.2 项目详情内聚能力

以下模块不再作为默认顶级入口，合并为项目详情页标签或二级入口：

- 合同：项目合同、金额、签约状态、履约节点。
- 风险：项目风险清单、概率/影响、缓解措施、关闭状态。
- 质量：质量标准、检查记录、不合格项、整改关联。
- 资源：设备、材料、车辆等项目资源计划和状态。
- 项目流程模板：从独立 `/projects/lifecycle` 逐步迁移到 `/projects/:id/lifecycle`。

### 4.3 降级或隐藏能力

- 论坛：默认隐藏；如保留，仅作为项目讨论或问题评论，不保留独立论坛入口。
- AI 助手：降级为实验功能，不进入默认菜单。
- 数据治理：从项目管理主线移除，保留为后台技术能力或后续平台化专项。
- 知识库：默认不进入第一版主线；如确需使用，放入系统管理或项目文档。
- 草稿箱：合并到报告、隐患、审批表单内部，不保留独立菜单。
- 通知设置、个人中心：放到用户头像/个人入口，不占业务主菜单。

## 5. 分阶段实施计划

### Phase 0：冻结扩张面

目标：阻止非主线模块继续变成顶级入口。

工作项：

- 审核 `src/app/route-map.js` 和 `src/app/menu.config.js`，标记顶级保留、隐藏、合并、实验功能四类入口。
- 新增一个轻量配置字段，例如 `visibility: 'main' | 'secondary' | 'hidden' | 'experimental'`，用于菜单收敛，不急于删除 route。
- 明确 `src/pages/*` 和 `backend/routers/*` 只做兼容，不新增业务页面或新业务 router。

验收标准：

- 默认主菜单只显示 7 个主入口。
- 隐藏入口仍可通过直接路由访问，避免第一阶段破坏已有页面。
- 不新增外部依赖，不做数据库迁移。

### Phase 1：主线菜单与页面壳收敛

目标：把用户日常工作路径收敛到项目交付闭环。

工作项：

- 调整菜单为“仪表盘、项目管理、任务管理、随手拍/隐患、报告中心、审批中心、系统管理”。
- 项目列表进入项目详情后，提供统一标签壳：概览、任务/WBS、隐患、报告、审批、合同、风险、质量、资源、归档。
- 将合同、风险、质量、资源的顶级入口隐藏，但保留组件/API，作为项目详情标签的后续接入对象。
- 将通知、个人中心移出业务菜单，迁移到顶部用户区。

验收标准：

- 新用户在默认菜单中只能看到主流程入口。
- 合同、风险、质量、资源不再与项目管理并列展示。
- 页面跳转路径能表达“所有业务对象围绕项目发生”。

### Phase 2：核心数据闭环

目标：优先消除核心主线的 mock 数据。

工作项：

- 项目管理：`useProjects` 接真实项目列表、创建、更新、删除接口；项目卡片指标来自后端或明确标记为后端待补。
- 任务管理：`useTasks` 接任务/WBS/甘特接口，保留现有 WBS 工具函数用于前端展示和计算。
- 随手拍/隐患：接真实隐患列表、创建、状态流转；移动端随手拍与 Web 隐患列表保持同一状态模型。
- 报告中心：接报告列表、提交、审批状态；草稿只作为报告内部状态。
- 审批中心：统一前后端接口，将前端 `/approval/tasks` 修正为后端真实契约，或在后端补兼容 endpoint。

验收标准：

- 项目、任务、隐患、报告四个主入口不依赖本地 mock 数据完成基础列表渲染。
- 断网或接口失败时显示明确空态/错误态，不静默伪造业务数据。
- 审批中心能处理至少一种真实业务对象，例如报告审批或隐患验收。

### Phase 3：项目详情内聚模块

目标：把工程项目必要但低频的合同、风险、质量、资源沉入项目上下文。

工作项：

- 合同标签：按 `project_id` 过滤合同，展示合同金额、状态、签约/履约日期。
- 风险标签：按 `project_id` 过滤风险，展示风险等级、概率、影响、缓解措施、关闭状态。
- 质量标签：按 `project_id` 展示质量检查记录和不合格项，必要时关联隐患整改。
- 资源标签：按 `project_id` 展示资源状态，不再承担完整资源调度系统职责。
- 项目生命周期：从通用模板页逐步迁移到具体项目详情内，保留模板选择但弱化独立入口。

验收标准：

- 以上模块必须通过项目详情访问，默认不出现在顶级菜单。
- 每个模块至少支持按项目过滤，避免全局列表脱离项目语境。
- 模块数据能反哺项目概览指标，例如风险未关闭数、质量不合格项、合同金额。

### Phase 4：清理遗留和实验面

目标：完成业务和代码层面的收敛。

工作项：

- 评估是否删除或归档论坛独立页面/API；若保留，改为项目讨论能力。
- 评估 AI 助手是否继续作为实验功能；未形成稳定场景前不进默认菜单。
- 数据治理、知识库等平台能力从 PMS 主线中移除，另开平台化专项时再恢复。
- 梳理 `src/pages/*` 与 `backend/routers/*` legacy 面，能迁入 `src/features/*` 和 `backend/api/routers/*` 的逐步迁入。

验收标准：

- 默认信息架构不再暴露非主线平台能力。
- legacy 面没有新增业务功能。
- README、菜单说明、API 文档与实际主菜单一致。

## 6. 保留、合并、隐藏、删除清单

| 模块 | 建议动作 | 理由 |
| --- | --- | --- |
| 仪表盘 | 保留 | 领导和项目负责人需要项目状态总览。 |
| 项目管理 | 保留并强化 | 业务主线入口。 |
| 项目流程模板 | 合并 | 迁入项目详情或项目创建流程。 |
| 任务/WBS/甘特 | 保留并强化 | 项目执行主链路。 |
| 随手拍/隐患 | 保留并强化 | 现场人员核心入口。 |
| 报告中心 | 保留 | 项目过程沉淀和审批依据。 |
| 审批中心 | 保留但限域 | 仅服务报告、隐患验收、阶段门等主线审批。 |
| 合同管理 | 合并 | 作为项目附属对象，不做独立合同系统。 |
| 风险管理 | 合并 | 进入项目详情风险标签。 |
| 质量管理 | 合并 | 进入项目详情质量标签，可关联隐患整改。 |
| 资源调度 | 合并 | 进入项目详情资源标签，先做状态展示。 |
| 组织架构 | 放入系统管理 | 管理配置，不是日常业务主线。 |
| 用户/角色 | 放入系统管理 | 权限配置，不占业务主菜单。 |
| 通知 | 弱化 | 顶栏或消息抽屉即可。 |
| 草稿箱 | 合并 | 进入报告/隐患表单内部。 |
| 论坛 | 隐藏或删除 | 与项目交付闭环弱相关。 |
| AI 助手 | 实验隐藏 | 当前不是主线刚需。 |
| 数据治理 | 移除主线 | 属于平台治理专项。 |
| 知识库 | 隐藏或放系统管理 | 非第一版主线。 |

## 7. 技术边界

- 不做一次性大删除；第一轮只收敛可见入口和路由展示。
- 不直接编辑自动生成 CRUD 代码；必要变更通过上层 feature API 或新 Layer 3 router 兼容。
- 不新增第三方依赖。
- 不改变鉴权和权限模型的基本形态，但要保证隐藏菜单不是权限控制的替代品。
- 不把合同、风险、质量、资源的数据模型强行合并；只合并产品入口和项目上下文。

## 8. 验证计划

### 静态验证

- `npm run lint`
- `npm run build`
- 后端相关变更运行 `pytest tests/ -v` 或更小范围的目标测试。

### 业务验证

- 登录后默认菜单只出现目标 7 项。
- 从项目列表进入项目详情后，能找到任务、隐患、报告、审批等主流程入口。
- 隐藏模块不在菜单出现，但直接路由不应在第一阶段破坏。
- 项目、任务、隐患、报告页面不再使用本地 mock 数据完成正常业务展示。
- 审批中心至少能完成一个真实审批动作。

### 回归验证

- 移动端保留首页、随手拍、任务、项目、审批、我的等核心路径。
- 既有 API 响应格式仍符合 `docs/API.md` 的通用响应结构。
- 菜单配置和路由配置之间没有断链。

## 9. 风险与缓解

| 风险 | 缓解 |
| --- | --- |
| 直接删除模块导致已有页面或测试失败 | 先隐藏菜单，不删除 route/API。 |
| 合同、风险、质量、资源被误删 | 只降级为项目详情标签，保留数据模型和 API。 |
| 主线页面仍依赖 mock，菜单收敛后显得功能变少 | Phase 2 优先补真实 API 闭环。 |
| 审批中心泛化为 OA | 限定审批对象为报告、隐患验收、阶段门。 |
| 文档和实现再次漂移 | Phase 4 同步 README、API、菜单说明。 |

## 10. 第一批建议任务

1. 给 `ROUTE_META` 增加模块分级字段，标记主线、二级、隐藏、实验。
2. 调整 `MENU_ITEMS` 默认只展示 7 个主入口。
3. 新增项目详情标签壳，把合同、风险、质量、资源作为项目上下文入口占位。
4. 修正审批中心前后端契约，优先支持报告审批或隐患验收。
5. 将 `useProjects`、`useTasks`、`useHazards`、`useReports` 从 mock 数据迁到真实 API。
6. 更新 README 和菜单说明，明确当前版本的业务主线。

## 11. 停止条件

第一批改造完成的停止条件：

- 默认菜单收敛到 7 项。
- 核心业务闭环能从项目进入任务、隐患、报告、审批。
- 合同、风险、质量、资源不再是顶级默认入口。
- 项目、任务、隐患、报告至少完成列表级真实 API 接入。
- lint/build/目标测试通过，或明确记录无法运行的环境原因。
